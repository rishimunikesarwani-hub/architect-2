## Evidence and status rules

- **Recorded UI proof:** a named journey in [the core browser verification record](2026-10-05-browser-verification.md) or [extended parity verification](2026-10-05-parity-verification.md), observed and reported by the main agent. This audit did not repeat browser operations. These records do not prove every menu, connector or scenario works.
- **Code present, UI unverified:** inspected implementation exists, but no matching browser result is recorded.
- **Partial:** a group is represented, but a documented part of its user flow is absent. Dummy implementations can satisfy the assignment if the flow is complete and honestly labeled.
- **Missing:** no corresponding control/state flow in the inspected source. A label, source-code export, generic message or architecture diagram does not substitute for the feature.
- **Pending external setup:** implementation exists, but configuration or a real integration check is incomplete.
- **In progress:** source was changing in this session. Re-audit after the edit and relevant UI check; do not count the prior browser record as proof of later changes.

Code line numbers are navigation anchors from this audit snapshot and may shift during ongoing edits. Function/component names identify the authoritative behavior.

## Final automated release verification

After the implementation agents stopped, the independent audit agent reran `npm test` and `npm run build` on 2026-10-05. All **19 tests across 3 files passed**; the build passed frontend TypeScript checking, synchronized the diagram artifacts and produced `runs/dist`. These existing tests cover backend project access, import boundaries and sample preview behavior; they do not establish that every newly added UI flow works.

The source/public/build copies of the production Markdown, production SVG and prototype SVG matched by SHA-256 after the build. No `.env*` file was present in `runs/dist`. `git check-ignore` confirmed local/production environment files, `.convex` state and build output are excluded; `.env.example` is intentionally retainable. `.vercelignore` excludes local environment files and `runs`, so a hosted upload is rebuilt instead of publishing the locally configured bundle. A bounded common-token/private-key pattern scan of candidate project text found no matches; this is a heuristic check, not a comprehensive secret-security guarantee.

The inspected [release guide](../docs/guide-release.md) explicitly keeps the first public demo disconnected from the backend until its HTTPS origin and Google round trip are configured/tested. It requires a fresh live-site check after approval and distinguishes repository/hosting publication from the unperformed hiring-form submission. No deploy, push or remote creation occurred during this verification.

Where a feature is present in code but unverified, run a targeted UI check rather than rebuilding it. Where only an index summary is available, implement a bounded, labeled prototype around that documented capability without claiming exact source-product behavior. Record the resulting evidence against the relevant row; do not flip all rows to complete because the build or 19 tests pass.

**Completion decision:** full requested completion remains pending real Google setup, the authenticated browser-to-Convex journey and public shipping. The representative local feature journeys above are verified to the extent explicitly reported; pending additions and specific unobserved edges retain their labels. A simulated generated-app deployment does not satisfy shipping the prototype. The permitted dummy flows and proposed production/multiplayer architecture do not require implementing every cloud service before handing over this prototype.
